## 1. 给下一位 AI 的任务

请先诊断，不要直接继续叠加补丁。用户的真实现象是：

- 打开其他程序后，桌面播放器有时不暂停。
- 某些情况下，打开其他程序的过程中播放器反而开始播放。
- 自动化脚本曾显示通过，但用户实际使用仍然失败。

目标行为：

1. 桌面没有其他程序窗口时，播放器允许播放。
2. 任何普通程序窗口出现在桌面之上时，播放器约 500ms 淡出，然后真正暂停。
3. 所有阻挡窗口消失并回到桌面后，如果此前是自动暂停，立即恢复。
4. 如果用户手动按了暂停，回到桌面也不能自动恢复。
5. 主题初次加载期间如果打开了其他程序，不能在稍后音频准备完成时突然开始播放。

最重要的诊断要求：先记录用户真实失败时 Windows 返回的窗口句柄、窗口类、进程、播放器状态和状态机动作，再决定修复方案。

## 4. v1.0.0 原始判断逻辑

v1.0.0 使用：

```text
src/XYDesktopPlayer.App/FullscreenWindowDetector.cs
src/XYDesktopPlayer.App/FullscreenPlaybackController.cs
src/XYDesktopPlayer.Core/FullscreenPlaybackPolicy.cs
```

检测器读取：

- `GetForegroundWindow()`：Windows 当前输入前台窗口。
- `GetAncestor(..., GA_ROOT)`：取根窗口。
- 窗口所属进程、类名、可见性、最小化、DWM cloaked 状态。
- 最大化状态、窗口边界、显示器边界。

虽然类名叫 `FullscreenWindowDetector`，并且采集了最大化与边界数据，但 v1.0.0 的最终策略并没有使用这些几何信息。只要当前前台窗口：

- 不是本播放器进程；
- 不是被列为桌面/Shell 的窗口类；
- 可见；
- 未最小化；
- 未被 DWM 隐藏；

就直接返回“阻挡播放”。所以 v1.0.0 的真实语义也是“其他普通前台窗口”，并不是严格的全屏检测。

因此，简单恢复 `IsZoomed`、窗口矩形、显示器矩形，不一定能修复现在的问题。这些字段在旧策略中是死数据。

## 5. 主题骨架版发生过的相关变化

### 5.1 主题加载改变了首播时机

v1.0.0 在 Web 页面导航完成后启动播放监控和首播。

主题骨架版必须先把主题清单和歌曲发送给共用播放器，所以把首播放到了 Web 页面发出 `theme-ready` 消息之后：

```text
PlayerForm.OnWebMessageReceived -> theme-ready
```

这会扩大一个竞态窗口：桌面状态在第一次判断后仍可能变化，而音频稍后才真正准备完成。

### 5.2 检测器被简化和重命名

提交：

```text
6faa04d refactor: simplify foreground playback monitoring
```

变化包括：

- `FullscreenWindowDetector` 改为 `ForegroundWindowDetector`。
- `FullscreenPlaybackController` 改为 `ForegroundPlaybackController`。
- 删除最大化、窗口矩形和显示器矩形采集。
- 保留 `GetForegroundWindow()` 为唯一的窗口来源。

这次删除没有直接删掉参与旧策略判断的条件，但它也没有解决“用户要检测所有桌面上方窗口，而代码只检测一个前台窗口”的结构性偏差。

### 5.3 500ms 淡出代码没有被删除

淡出仍在：

```text
src/XYDesktopPlayer.App/WallpaperEngineShim.cs
```

当前流程是：

1. 找到所有正在播放的、由 shim 跟踪的 `Audio`。
2. Web Audio `masterGain` 在 500ms 内线性降到 0。
3. 等待约 500ms。
4. 把仍在播放的音频加入 `fullscreenPausedAudio` 集合并调用 `audio.pause()`。
5. 自动恢复时只恢复这个集合中的音频，因此理论上不会恢复用户手动暂停的音频。

所以当前失败更可能发生在“何时调用暂停/恢复/首播”，而不是淡出函数本身消失。

## 6. 当前代码的完整判断逻辑

### 6.1 每 500ms 只看一个前台窗口

文件：

```text
src/XYDesktopPlayer.App/ForegroundWindowDetector.cs
```

伪代码：

```text
foreground = GetForegroundWindow()
if foreground == 0:
    return Unknown/default

root = GetAncestor(foreground, GA_ROOT)
读取 root 的 PID、className、visible、minimized、cloaked

IsOwnProcess      = PID == XYDesktopPlayer PID
IsDesktopSurface  = className 是 Progman 或 WorkerW
IsShellOverlay    = className 是 Shell_TrayWnd、Shell_SecondaryTrayWnd 或 #32768
```

异常被完全吞掉并返回 `default`。当前日志不会记录异常发生在哪个 API，也不会记录失败窗口。

### 6.2 阻挡、允许播放和中立状态

文件：

```text
src/XYDesktopPlayer.Core/ForegroundPlaybackPolicy.cs
```

当前分类效果：

| 当前前台对象 | `ShouldBlockPlayback` | `CanStartOrResumePlayback` | 含义 |
|---|---:|---:|---|
| 普通外部程序窗口 | true | false | 要暂停 |
| 播放器自己的窗口 | false | true | 可播放/恢复 |
| `Progman`、`WorkerW` | false | true | 可播放/恢复 |
| 任务栏、弹出菜单 | false | false | 中立，保持此前状态 |
| 没有前台窗口、检测异常 | false | false | 中立，保持此前状态 |
| 不可见、最小化、cloaked | false | false | 中立 |

上一次修复前，所有 Shell 类都只被看作“不阻挡”，这会让任务栏或弹出菜单错误触发恢复。提交 `24a1353` 把“真实桌面”和“Shell 浮层”拆开，只允许真实桌面或播放器窗口触发首播/恢复。

### 6.3 播放状态机

文件：

```text
src/XYDesktopPlayer.App/ForegroundPlaybackController.cs
```

计时器间隔：500ms。

内部状态：

```text
_wasBlocked       上一次被认为是否有外部窗口
_autoPauseArmed   是否已经由程序自动暂停，决定以后能否自动恢复
_startupPending   首播是否正在等待桌面可用
_checking         是否正在执行一次异步暂停/恢复，防止重入
```

状态动作：

```text
此前未阻挡 + 现在阻挡
    -> Pause
    -> 调用 JS 500ms 淡出暂停
    -> _autoPauseArmed = true

此前阻挡 + 现在不阻挡 + 确认真正回到桌面/播放器 + 自动暂停已武装
    -> Resume
    -> 立即恢复由自动暂停集合保存的音频

startupPending + 确认真正回到桌面/播放器
    -> Start
    -> 清掉 startupPending
    -> 调用首播回调
```

重要问题：`Start` 分支在调用首播回调之前就把 `_startupPending` 清掉。如果回调失败、音频仍未准备好，或者回调执行过程中前台窗口已经变化，状态机不会自然重试。

### 6.4 首播有最长 3 秒的检查与使用时间差

文件：

```text
src/XYDesktopPlayer.App/StartupPlaybackService.cs
```

当前首播逻辑：

```text
先在 C# 中判断一次当前是桌面/播放器
然后进入 WebView JavaScript
最多等待 3 秒，每 50ms 查询 audioPrepared
一旦 audioPrepared，就直接 __xyDesktopStartPlayback()
```

等待这 3 秒的 JavaScript 循环完全不知道 Windows 前台窗口是否已经变化。

这提供了一个非常符合用户现象的竞态：

1. 主题刚发出 `theme-ready` 时，C# 看到的是桌面，允许首播。
2. `TryStartAsync` 进入最长 3 秒的音频准备等待。
3. 用户在此期间打开其他程序。
4. 音频稍后变为 ready，JavaScript 仍然直接开始播放。
5. 直到下一次 500ms 窗口轮询才可能触发淡出暂停。

用户听到的就是“打开窗口后反而开始播放”。这个竞态在上一次修复中没有被消除。

## 7. 为什么还会出现“窗口打开但不暂停”

目前有几项结构性原因。下面区分确定事实和待验证假设。

### 7.1 确定的设计偏差：只检测前台窗口，不检测所有可见程序窗口

用户后来的明确需求是“只要打开任何程序在桌面之上就暂停”。

但当前代码只调用 `GetForegroundWindow()`，并没有枚举所有非最小化、可见、位于桌面之上的顶层窗口。

因此这些情况可能漏报：

- 程序窗口已经显示，但 Windows 输入前台暂时还是任务栏或某个 Shell 浮层。
- 多显示器上另一个程序窗口可见，但当前前台焦点仍在桌面/播放器。
- 某个程序使用不抢焦点或 `WS_EX_NOACTIVATE` 的可见窗口。
- 用户看到窗口“在桌面上”，但 Win32 的 foreground 语义并不等同于视觉上的“存在于桌面之上”。

如果严格按用户需求，应该研究 `EnumWindows`/Z-order/可见区域，而不是继续只修补 `GetForegroundWindow()` 的类名表。

### 7.2 确定的延迟：最坏约 1 秒后才真正暂停

检测轮询最长先等约 500ms，淡出又等约 500ms，才调用 `audio.pause()`。

所以从外部窗口出现到真正暂停，理论最坏值接近 1 秒。短暂切换窗口时，用户可能看到状态机尚未完成，或者先暂停后又恢复。

### 7.3 确定的并发限制：淡出期间不再处理新状态

`OnTimerTick` 是异步方法，并用 `_checking` 防止重入。500ms 淡出期间后续 tick 会直接返回。

如果窗口在淡出期间又发生变化，控制器只能等本次异步动作完成，再等下一次 tick 才修正状态。快速 Alt+Tab、任务栏预览和启动窗口动画可能产生明显错序。

### 7.4 待验证：真实失败窗口被错误分类

上一次修复删除了两个过于宽泛的 Shell 类：

```text
Windows.UI.Core.CoreWindow
XamlExplorerHostIslandWindow
```

因为这些名称不一定只属于桌面 Shell。但仍然可能有其他真实应用类名、根窗口、cloaked 状态或可见性与预期不同。

当前程序没有记录实际失败窗口的以下信息，因此不能证明是哪一项：

- foreground HWND 和 root HWND；
- PID、进程名、可执行路径；
- className、窗口标题；
- visible、iconic、cloaked；
- window style、extended style；
- 窗口矩形、显示器、Z-order；
- 最终分类与采取的动作。

### 7.5 待验证：用户实际运行的仍是另一个包

由于单实例互斥量存在，而且之前查询正在运行进程的路径时被系统拒绝访问，所以不能排除用户测试的是旧实例。

这不是把问题推给用户，而是当前交接必须补齐的证据。下一位 AI 应在修改代码前先读取实际进程路径。

## 9. 为什么原来的自动测试会给出假安全感

### 9.1 `FullscreenPauseAcceptance.ps1`

这个脚本实际上用的是：

```text
-Mode window
```

不是用户日常使用的 WorkerW 桌面模式。

它创建一个普通 WinForms `Form`，设为 TopMost，并反复用 `SetForegroundWindow`、`BringWindowToTop` 强行切换焦点。恢复阶段又把播放器普通窗口本身强行设为 foreground。

它证明的只是：

> 对一个已知 WinForms 窗口类，在被脚本强制设为前台时，策略可以调用一次暂停；播放器普通窗口被强制设为前台后可以调用一次恢复。

它没有证明：

- WorkerW 桌面模式下的真实用户流程；
- 从任务栏、开始菜单、Alt+Tab 打开程序；
- Explorer、浏览器、WinUI/UWP、游戏等不同窗口模型；
- 主题加载和首播竞态；
- 多显示器与可见但不在 foreground 的窗口。

### 9.2 `StartupPlaybackAcceptance.ps1`

这个脚本使用桌面模式，但仍通过一个 TopMost WinForms 测试窗和 `ForceForeground` 强行维持前台，然后强行把 `GetShellWindow()` 设置为 foreground。

它没有在 3 秒音频准备等待期间插入一次真实程序启动，因此没有捕获“判断时是桌面、真正 play 时已经是外部程序”的竞态。

### 9.3 现有核心测试只验证布尔输入，不验证 Win32 事实

核心测试手工构造：

```text
IsDesktopSurface=true/false
IsShellOverlay=true/false
IsVisible=true/false
```

这些测试能验证状态机函数，但不能证明 Windows 对用户实际窗口返回的值就是测试所假设的值。

## 10. 当前日志为什么无法定位问题

日志目录：

```text
C:\Users\Administrator\AppData\Local\XYDesktopPlayer\Logs
```

`ApplicationLog` 当前主要写：

- 应用启动；
- 应用退出；
- 未处理异常；
- 内容/主题加载失败。

正常运行时的前台窗口采样、分类、暂停、恢复和首播动作都没有写入这个日志。

验收脚本的 `TraceCapture` 只在带 `--capture` 参数时写独立 trace，不是用户日常运行日志。因此用户报告失败后，现有日志无法回答：

- 当时 `GetForegroundWindow()` 返回了谁；
- 为什么策略认为可以继续播放；
- 调用了 Start、Resume 还是根本没有检测到变化；
- 用户是否运行了预期的二进制包。

这是此前诊断过程最大的缺口。

## 11. 建议下一位 AI 先做的诊断版本

不要先改变判断结果。先加一个可开关的详细日志，例如托盘菜单“窗口检测调试日志”。每次窗口事件或分类发生变化时记录：

```text

foreground HWND
root HWND
PID
process name and executable path
window title
class name
visible

cloaked
window style / extended style
window rectangle
monitor rectangle
IsOwnProcess
IsDesktopSurface
IsShellOverlay
```

日志不要每 500ms 无限制刷同样内容。可以只在 HWND、分类或状态动作发生变化时写，并保留最近几十次采样的环形缓冲；用户点“导出诊断”时一次性写文件。

同时建议用 `SetWinEventHook(EVENT_SYSTEM_FOREGROUND)` 记录真实前台变化。即便最终仍使用轮询，它也能证明窗口切换顺序。

## 12. 推荐重新设计的方向

### 12.1 先明确语义：前台窗口还是所有桌面上方窗口

根据用户当前表达，应按“所有可见程序窗口”实现，而不是“一个输入 foreground 窗口”。

可以研究：

```text
EnumWindows
IsWindowVisible
IsIconic
DwmGetWindowAttribute(DWMWA_CLOAKED)
GetWindowLongPtr(GWL_STYLE / GWL_EXSTYLE)
GetWindowRect / DWMWA_EXTENDED_FRAME_BOUNDS
GetWindow(GW_OWNER)
GetWindowThreadProcessId
```

建议定义一个 `WindowPresenceDetector`：枚举顶层窗口并判断是否存在至少一个阻挡窗口，而不是只返回 foreground。

至少排除：

- 播放器自己的进程和子窗口；
- Explorer 的 `Progman`、实际承载桌面图标的 `WorkerW`；
- 任务栏以及用户明确不希望算作程序的 Shell 浮层；
- 不可见、最小化、DWM cloaked、零尺寸、完全不在任一显示器可视区域的窗口。

对于 tool window、无激活窗口、拥有者窗口、桌面小组件，需要先从诊断日志观察真实情况，再决定是否排除。

### 12.2 把“用户意图”和“环境暂停”分开

当前 `_autoPauseArmed` 是一个较脆弱的布尔值。更稳妥的模型：

```text
UserIntent: Playing / Paused
ThemeReady: true / false
SuspensionReasons: set，例如 ExternalWindow
ActualAudioState: Playing / FadingOut / Paused / Starting
```

唯一播放条件：

```text
desiredPlaying =
    UserIntent == Playing
    && ThemeReady
    && SuspensionReasons 为空
```

这样：

- 手动暂停直接改变 `UserIntent`，环境恢复不能覆盖它。
- 外部窗口只增加/删除 `ExternalWindow` 原因。
- 初始自动播放只是把 `UserIntent` 设为 Playing；如果仍有阻挡原因就继续等待。
- 主题切换、导航、桌面模式切换不需要重用含义模糊的 `_startupPending`。

### 12.3 消除 3 秒首播竞态

不要在确认桌面一次之后，进入一个可能等待 3 秒再播放的 JS 循环。

建议拆成两步：

1. 页面只准备音频，准备好后向宿主发送 `audio-ready`。
2. 宿主收到 `audio-ready` 后重新做一次完整窗口存在性检查；只有此刻仍无阻挡窗口才调用一次 `play`。

还应在异步 `play` 返回后再次采样。如果期间已经出现阻挡窗口，应立即进入淡出/暂停或取消本次 start token。

当前控制器在 Start 回调执行前就清掉 `_startupPending`，建议改成只有“音频成功开始且启动时仍无阻挡”后才清除。

### 12.4 让异步动作可取消且幂等

可使用单调递增 generation/token：

- 每次窗口状态、用户意图或主题变化都增加 generation。
- Pause/Resume/Start 在 await 前保存 generation。
- await 返回后如果 generation 已变化，不再提交旧状态。
- 对同一 desired state 重复调用不应产生新的声音或重置手动暂停。

现有 JS 淡出已经有 `fadeGeneration`，但 C# 的状态机和首播没有同等级别的取消机制。

## 13. 必须覆盖的真实验收矩阵

不要只用自建 WinForms 窗口。至少用发布包的桌面模式逐项验证：

1. 从纯桌面启动播放器，自动播放。
2. 打开资源管理器普通窗口。
3. 打开 Chrome/Edge 普通窗口。
4. 打开 Windows 设置或其他 WinUI/UWP 应用。
5. 普通窗口、最大化窗口、真正全屏窗口各一次。
6. 从任务栏单击已打开程序。
7. 只悬停任务栏缩略图，不切入程序；记录预期行为。
8. Alt+Tab 快速来回切换。
9. Win+D 显示桌面，再恢复窗口。
10. 把所有程序最小化，然后逐个恢复。
11. 多显示器：播放器在主桌面，另一个显示器有普通窗口。
12. 播放器启动/主题加载期间立即打开其他程序，等待超过 3 秒。
13. 用户手动暂停后打开程序并回桌面，必须继续暂停。
14. 自动暂停后切歌、切主题，再回桌面。
15. Explorer 重启后重新嵌入桌面，再重复以上关键步骤。

每个步骤应同时记录：

- 屏幕录制或精确时间点；
- 新诊断日志；
- 实际运行 EXE 路径；
- 播放器 UI 状态与真实声音状态。
